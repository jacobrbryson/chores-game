# AGENTS.md

## Purpose
This file defines what this project is trying to accomplish and the operating rules for contributors (human and AI agents). Treat it as a living document and update it as decisions are made.

## Roadmap
Planned and in-flight work lives in `docs/ROADMAP.md`. This file records durable rules and decisions already made; the roadmap records what is next. Keep them in sync — when a roadmap item ships, move the decision here.

## Product Goal
Build a family chore game where:
- Parents manage chores, approvals, and rewards.
- Kids complete chores, earn virtual currency after approval, and spend it on cosmetic avatar items.

## Primary Roles
- Parent (`admin`)
  - Creates and assigns chores/checklists.
  - Reviews submitted chores and approves or rejects them.
  - Manages reward/store catalog.
- Kid (`player`)
  - Signs in with Google.
  - Views assigned chores.
  - Submits chores as complete.
  - Earns currency when submissions are approved.
  - Purchases and equips cosmetics.

## Core Requirements (MVP)
1. Authentication
   - Google auth for kids and parents.
   - Role-based access (`admin`, `player`) enforced in backend and UI routing.
2. Chore Workflow
   - Chore states: `Open -> Submitted -> Approved | Rejected`.
   - Only parents can approve/reject.
   - Rejections should include optional feedback.
3. Parent Notifications
   - Notify parent when a kid submits a chore.
   - MVP can start with in-app notifications; external channels (email/push) are optional follow-up.
4. Economy
   - Virtual currency balance per kid account.
   - Balance increases only on approved submissions.
   - All balance mutations must be auditable.
5. Shop + Inventory
   - Parent-configurable cosmetic items with price and availability.
   - Kids can purchase items if balance is sufficient.
   - Purchased items are stored in inventory and can be equipped.
6. Avatar/Cosmetics
   - Kid avatar supports cosmetic slots (for example: hat, outfit, accessory).
   - Equipped cosmetics persist per user.

## Domain Rules
- Approval is the single trigger for payout.
- A chore submission can only be approved/rejected once per submission event.
- Currency cannot go negative.
- Purchase operations must be atomic (deduct balance + grant item together).
- Role checks are mandatory on all protected API operations.

## Engineering Rules
- Keep business logic in shared/domain modules, not only UI handlers.
- Validate all incoming API payloads.
- Prefer explicit enums/constants for statuses and roles.
- Every change that adds or modifies user-facing text must update the shared locale files in the same change set.
- Do not hardcode user-facing strings in web or mobile UI when a shared locale key should be used instead.
- Add or update stable translation keys whenever UI copy changes, and keep supported locale files synchronized.
- Initial supported locale files are `fr-FR`, `en-US`, and `es-US`, in that order.
- All new user-facing features must explicitly consider:
  - Localization for `fr-FR`, `en-US`, and `es-US`.
  - Web and mobile parity; implement in both apps where applicable and document intentional exceptions.
  - Support visibility; support operators should be able to inspect or report on the feature where practical.
  - Auditability; important state changes should be logged or otherwise diagnosable.
- Any new feature, notable user-facing change, or bug fix should add or update an entry in the web changelog JSON.
- Changelog dates are included in the sitemap automatically via `apps/web/src/app/sitemap.ts`, which reads from the changelog JSON at build time — no manual sitemap edits needed when adding changelog entries.
- Changelog entries must include `image`, `date`, `type`, `subject`, and `description`.
- User-facing changelog page labels must be localized in all supported locale files.
- Keep changelog entries concise and user-friendly; do not include internal implementation details.
- Do NOT add changelog entries for the support console / operator-facing support tooling (the `/support` console, support-request triage, operator workflows, etc.). The changelog is for end users, who never see these surfaces. User-facing support features (e.g. submitting bug reports/feedback from the app) are fine; internal support operations are not.
- Use `Language` in product UI labels and forms; reserve `locale` for code, config, payloads, and storage fields.
- Use shared select/dropdown form components for language selection; do not introduce one-off select styling for locale pickers.
- Quest content must localize player-visible title, description/summary, page text, choice labels, reward text, locked/error copy, and relevant image/audio metadata when present.
- Quest packages must include localized content for supported languages or valid fallback content that resolves through the quest locale chain.
- Use the shared Tailwind `Alert` component for all in-app alert/error/warning/info UI; do not introduce one-off alert markup or alert-specific CSS for new surfaces.
- Never use browser-native dialogs (`window.alert`, `window.confirm`, `window.prompt`) for product UI flows; always use shared modal/dialog components (for example `ModalShell` + shared `Button` patterns).
- Action-menu behavior must match shared app menu UX: selecting a menu action should close the menu immediately and then open the destination modal/dialog/surface if needed.
- Every disabled button/control must carry a tooltip (`title`) that explains *why* it is disabled and, where possible, how to enable it (for example "Sorting is on — choose Manual order to move chores"). Note that browsers suppress native `title` tooltips on disabled form controls, so wrap disabled controls in a hoverable element (see `MenuActionButton`) rather than putting `title` directly on the disabled `<button>`. Also give disabled controls a clear disabled appearance (reduced opacity / `not-allowed` cursor) so they don't look interactive.
- For page-level and card-level async data fetches, use visual skeleton loaders instead of loading text whenever practical (for example avoid plain `Loading ...` copy as the primary loading state).
- Keep source files small and focused. Target a max of ~400 lines per file; split large files by feature/component.
- Add tests for workflow-critical behavior:
  - chore status transitions
  - approval/rejection permissions
  - currency payout
  - purchase flow and insufficient funds
- E2E Testing:
  - Use Playwright for business-critical workflows.
  - Prefer a small number of high-value tests.
  - Avoid excessive brittle UI tests.
  - New major workflows should have E2E coverage.
  - Shared helpers should be reused.
  - E2E tests should focus on user outcomes, not implementation details.
- Avoid breaking changes to API contracts without updating this file.

## Data Classification
All new collections, documents, APIs, and fields must be classified into exactly one of these categories:
- `PUBLIC`
  - Approved changelog entries
  - Approved community awards
  - Approved SEO content
- `FAMILY_PRIVATE`
  - Chores
  - Rewards
  - Quest progress
  - Family activity feed
  - Achievement progress
- `CHILD_SENSITIVE`
  - Child names
  - Child avatars
  - Child activity history
  - Child preferences
  - Child login/session activity
- `ADMIN_ONLY`
  - Audit logs
  - Support notes
  - Moderation records
  - Consent history
  - Privacy requests
  - Internal reporting
- `SYSTEM_SECRET`
  - Tokens
  - OAuth credentials
  - Internal security metadata
  - Auth-provider identifiers
  - Encryption or signing secrets
- New features should document which classifications they introduce.

## AI Feature Rules
All AI-powered features must:
- Default OFF for child users.
- Require parent/admin enablement when applicable.
- Never train models using family data.
- Never expose one family's data to another family.
- Clearly identify AI-generated content where appropriate.
- Respect child privacy controls.
- Support complete family-level disabling.
- Be auditable when AI actions affect user data.

## Support Access Rules
Support access exists only for:

- abuse investigations
- privacy requests
- account recovery
- moderation workflows

Support operators may not:

Support actions should be auditable whenever practical.

## Feedback & Support Requests (Product Feedback Source of Truth)
The `supportRequests` collection is the single source of truth for all user-submitted feedback — bug reports, feature requests, questions, and general feedback. Do not build a parallel feedback/ticketing system; extend this one.

- **Storage:** `families/{familyId}/supportRequests/{id}` (classification: `ADMIN_ONLY` for operator fields; reporter-visible subset is `FAMILY_PRIVATE`). Domain logic + validation live in `apps/web/src/lib/support/requests.ts`; the cross-family read/filter/summary layer is `apps/web/src/lib/support/management.ts`.
- **Types:** `bug`, `feature`, `question`, `feedback`. Bugs are graded by `severity` (`low`/`medium`/`high`, required); non-bug types use the optional `importance` scale (`nice_to_have`/`useful`/`very_important`/`blocking`). The two are mutually exclusive per type — validation rejects severity on non-bugs and importance on bugs.
- **Status lifecycle (operator-managed):** `new → needs_info → triaged → planned → in_progress → released/done → closed`, plus `declined` and `duplicate`. `released`, `done`, `closed`, `declined`, `duplicate` are terminal (set `closedAt`). Legacy `triaged`/`done` remain valid; legacy stored values (`submitted`, `acknowledged`, `applied`, `rejected`) are normalized on read — never write them.
- **Submission:** users submit via `SupportRequestDialog` (4 entry points in `MyRequestsList`). Required: type, subject, description. Optional: severity/importance, category (bug/feature only), `allowContact`, `notifyOnStatusChange`. `POST /api/support/requests` persists + best-effort emails the support inbox.
- **Automatic diagnostics:** captured client-side (`lib/support/diagnostics.ts`, installed globally via `DiagnosticsBootstrap`): browser, OS, screen, language, app version, current URL; bug reports also attach recent console-error + API-failure ring buffers. Diagnostics are best-effort and must never block submission.
- **Email:** every submission emails `support@orcwood.com` (override `SUPPORT_INBOX_ADDRESS`) via the SES provider with `[BUG]/[FEATURE]/[QUESTION]/[FEEDBACK]` subject tags and a support-console deep link (`lib/support/notify-email.ts`). Reply-To is the reporter when they consented to contact. Requires `EMAIL_PROVIDER=ses` + `EMAIL_FROM_ADDRESS`; absence is tolerated.
- **Status-change notifications:** when an operator changes status and the reporter set `notifyOnStatusChange`, the reporter is notified in-app (admin-written `support_request_status_changed` notification, relatedIds-scoped) and by email (`lib/support/status-notify.ts`). Operators may attach an optional `publicMessage` shown to the reporter.
- **Support console (`/support/requests`):** filter by type/status/severity/importance/category/family/reporter/assignee + search; per-status/type summary cards. Detail view exposes metadata, diagnostics, contact/notify preferences, full history + audit + internal notes.
- **Operator actions (`PATCH /api/support/requests/{id}` with a `familyId` body):** change status, assign owner (`assignedToUid`/`assignedToEmail`), set category, mark duplicate (`duplicateOfId`), link related tickets (`relatedTicketIds`), link a changelog entry (`relatedChangelogEntryId`), toggle voting. Public visibility + public copy is managed via the `/public` sub-route (which scrubs private info). Every operator change writes a history entry + immutable audit log.
- **Internal notes:** `POST /api/support/requests/{id}/notes` writes to the `internalNotes` subcollection — visible only to support operators via the console; never exposed to end users.
- **Public voting & roadmap (schema-ready):** `isPublic`, `allowVoting`, and `votesCount` exist on the entity; the public requested-changes snapshot + voting service already consume them. The public voting UI is intentionally minimal/deferred — keep the data model ready rather than blocking on UI.
- **Changelog linkage:** operators set `relatedChangelogEntryId` to tie a shipped request to a `change-log.json` entry; reporters who opted in are notified when the status moves to `released`.
- **Support expectations:** treat this system as the canonical backlog for product feedback and roadmap. When triaging, set importance/severity and status accurately, assign an owner, and link duplicates/changelog entries so reporting and the public roadmap stay coherent. All operator mutations are audited; do not bypass the audit/history writes.

## Public Content Publishing / SEO
- Public SEO content comes only from support-approved curated content in `publicContent`.
- Public content must never expose private family, child, support, audit, source, or internal operator data.
- Content lifecycle is `draft -> review -> approved -> published -> archived`.
- Published content may be included in public routes and the sitemap when a real route exists.
- Voting and community signals are review-priority signals only and never publish, promote, or archive content automatically.
- Public content should stay locale-aware and JSON/export friendly.
- Public page metadata should come from the content SEO fields.
- Support manages content; the SEO dashboard reports metadata, readiness, sitemap, and lifecycle health.

  - An active daily, weekly, monthly, or custom recurring routine expires and materializes a fresh occurrence when its next scheduled date arrives, even when the prior occurrence was only partly complete. Instant recurrences remain completion-driven.

  - No new collections or classifications are introduced. Routine occurrence fields remain `FAMILY_PRIVATE`, completed child activity remains `CHILD_SENSITIVE`, and rollover audit records remain `ADMIN_ONLY`.

## Onboarding & Consent

Onboarding applies **only to family admins (parents)**. Child `player` accounts never see onboarding.

### First-run detection
A family is considered onboarding-complete when **either**:
- `families/{familyId}.onboardingCompletedAt` is set (new-style wizard), **or**
- `families/{familyId}.parentalConsentAt` is set (existing families that pre-date the wizard).

`GET /api/family/onboarding-status` evaluates both fields and returns `needsOnboarding` (show wizard) and `needsReacceptance` (show blocking re-accept modal). `DashboardHome` calls this on mount and acts accordingly.

### Onboarding wizard (`/onboarding`)
- Steps: Welcome → Family Name → Privacy & Consent → Add First Child (optional) → Create First Chore (optional) → Done.
- The Family Name step calls `POST /api/onboarding/complete` (sets `onboardingCompletedAt`, optionally renames the family).
- The Privacy & Consent step calls the existing `POST /api/family/privacy/consent` and records `TERMS_ACCEPTED`, `PRIVACY_ACCEPTED`, and `PARENTAL_CONSENT_RECORDED` events.
- Add Child and Create First Chore use the existing `/api/family/members` and `/api/chores` endpoints.
- Players who somehow navigate to `/onboarding` are redirected to `/` by the wizard's status check.

### Re-acceptance
When `consentUpToDate: false` for a completed family admin, `DashboardHome` shows a `ReacceptanceModal` that cannot be dismissed without accepting. It calls `POST /api/family/privacy/consent` and records new consent events. Use a blocking modal only — never a toast, banner, or notification.

### Privacy tab (Family → Privacy)
The Privacy tab at `/family?tab=privacy` is the ongoing privacy dashboard. It must remain accessible after onboarding for consent history, version info, data export, deletion requests, and child privacy settings. Do not move privacy controls away from the Family page.

### Rules
- Consent must be collected during onboarding for new users.
- Existing users with prior `parentalConsentAt` skip onboarding entirely.
- Version bumps to `CURRENT_TERMS_VERSION` or `CURRENT_PRIVACY_VERSION` trigger re-acceptance on next dashboard load.
- Child accounts (`player` role) receive 403 on all `/api/family/privacy/*` routes and never provide parental consent.
- Every consent action writes immutable records to `families/{familyId}/consentEvents` via `appendConsentEventBestEffort`.

## Discovery / What's New System
Discovery answers "what is new since I last looked?" — it is **separate from the notification system** (which answers "what happened?"). Discovery uses seen/unseen state, never notification read/unread state. Do **not** build a second notification system or add one-off badge logic per feature.

- **Section model.** All discoverable surfaces are registered as sections in `apps/web/src/lib/discovery/sections.ts` (`DISCOVERY_SECTIONS`). Current keys: `chores`, `store` (+ nested `store:customize_colors`, `store:customize_avatar`, `store:victory_confetti`, `store:family_awards`, `store:quest_items`), `quests`, `achievements`, `changelog`, `requested_changes`, `community_awards`. New discoverable features must register a section key and contribute a count in `counts.ts`/`service.ts` rather than adding bespoke badge logic.
- **State model.** Section-level last-seen timestamps (prefer over per-item rows) at `users/{profileUid}/discoveryState/{sectionKey}` with fields `sectionKey`, `lastSeenAt`, `seenByUid`, `seenByMemberId`, `updatedAt`. Nested store keys are encoded path-safely (`store:customize_avatar` -> doc id `store__customize_avatar`). No persistent per-item/per-user discovery rows; counts are derived from existing records (chores, family rewards, achievement progress, changelog JSON, quest `publishedAt`).
- **Active-profile scoping.** Discovery is scoped to the **active** signed-in profile (`session.uid`/`session.memberId`), including switched/managed child profiles — never blindly to the authenticated parent. A switched parent writes the child's state via the family-admin Firestore rule (`canAdminManageUser`), so switched-child discovery state never overwrites the parent's.
- **Server-side authorization.** All counts are computed server-side with the viewer's actual access (`apps/web/src/lib/discovery/service.ts`). Players only count their own visible/open chores and player-audience completed achievements; admins count family-wide. Admin-only sections (`community_awards`) are never exposed to players, and discovery payloads must not leak existence of inaccessible items.

## Privacy & Child Safety (read before adding any data-collecting or social feature)
Family Chores is **privacy-first and child-safety-first**. These rules are non-negotiable:
- **Classify data up front.** Apply the `Data Classification` section to every new collection, document, API, and field, and minimize child data within that classification.
- **Minimize child data.** Prefer deriving from existing data over storing new child-identifiable fields.
- **Apply AI governance without exception.** Follow `AI Feature Rules` for any AI-powered, child-facing, or family-data feature. The Privacy tab should only expose child controls when the underlying feature exists.
- **Voting is parent-only and never available to child accounts** (see the voting model note above; `players` cannot vote).
- **Public surfaces must follow SEO governance.** `PUBLIC` content must follow `Public Content & SEO Rules`; all other classifications stay off public/SEO pages.
- **User data controls live under Family, not a standalone route.** The Family page has a `Privacy` tab (admin-only) for the privacy overview, data summary, export, deletion request/cancel, child controls, and consent. Public legal pages stay separate.
- **Server-side authorization on every privacy endpoint.** All `/api/family/privacy/*` routes resolve the caller's family and require `admin` server-side (shared helpers in `apps/web/src/lib/family/access.ts`); never rely on client checks. Players/children get `403`.
- **Feature gating must stay server-enforced.** Privacy-sensitive and premium functionality must use entitlement-driven access with server-side checks; do not rely on UI gating alone.
- **Audit sensitive privacy/admin actions.** Export, deletion request/cancel, child-setting changes, and consent are written via `writeAuditLogBestEffort` to `families/{familyId}/auditLogs` (event types in `apps/web/src/lib/privacy/types.ts`, `PRIVACY_AUDIT_EVENTS`).
- **Export must be intentionally sanitized, not just redacted.** The user-facing family export (`GET /api/family/privacy/export`) must never return raw database records. Every entity type passes through an explicit allowlist sanitizer (`sanitizeMemberForExport`, `sanitizeInviteForExport`, `sanitizeChoreForExport`, `sanitizeRewardForExport`, `sanitizeQuestForExport`, `sanitizeFeedItemForExport`, etc.) defined in `apps/web/src/lib/privacy/export-sanitizers.ts`. Specific rules: (1) external OAuth/provider avatar URLs (`avatarPhotoUrl`, `lh3.googleusercontent.com`) are never exported — replace with `hasExternalAvatar: true` where relevant; (2) child (`player`) login and session timestamps (`lastSignInAt`, `lastActiveAt`) are excluded; (3) internal auth/Firebase UIDs (`createdBy`, `inviterUid`, admin-only fields) are excluded from invite and chore records; (4) stale invite orphans (invited email that already has an active member doc) are excluded; (5) the export manifest must list its sanitization notes via `EXPORT_MANIFEST_NOTES`. Admin/support exports are separate and must never be mixed into the family-facing export.
- **Deletion is scheduled, never an immediate hard delete.** `POST /api/family/privacy/deletion` sets `deletionRequestedAt` + `deletionScheduledFor` (now + 30 days, `DELETION_GRACE_PERIOD_DAYS`); `DELETE` cancels during the grace period. Irreversible purge is intentionally NOT implemented — see the SERVER-SIDE TODO in `deletion/route.ts`; the UI must continue to say deletion is *scheduled*.
- **Legal documents are versioned source files of truth.** Privacy Policy and Terms of Service content live in `apps/web/src/legal/privacy-policy.json` and `apps/web/src/legal/terms-of-service.json`. Their `version` fields are canonical. Public legal pages render from those files through the shared loader, and consent validation must use that same loader rather than duplicate version sources. When legal content materially changes, bump the file `version` and `effectiveDate` and set `requiresReacceptance: true`.
- **Legal loader is the single entry point.** `apps/web/src/lib/legal/loader.ts` exports `getPrivacyPolicy()`, `getTermsOfService()`, `getCurrentPrivacyPolicyVersion()`, and `getCurrentTermsVersion()`. `apps/web/src/lib/privacy/config.ts` re-exports `CURRENT_TERMS_VERSION` and `CURRENT_PRIVACY_VERSION` from the loader for compatibility. Avoid maintaining duplicate legal-version sources whenever practical.
- **Consent + versions: current state.** Family-level consent fields live on the family doc: `acceptedTermsVersion`, `acceptedPrivacyVersion`, `parentalConsentAt`, `parentalConsentByUserId`, `dataRegion` (default `US`). Current versions resolve through the shared legal loader via `apps/web/src/lib/privacy/config.ts`. `consentUpToDate` is a derived signal: all three must be present and versions must match the current legal source of truth.
- **Consent history: immutable append-only event log.** Every call to `POST /api/family/privacy/consent` appends three immutable records to `families/{familyId}/consentEvents` — one for `TERMS_ACCEPTED`, one for `PRIVACY_ACCEPTED`, and one for `PARENTAL_CONSENT_RECORDED` — via `appendConsentEventBestEffort` in `apps/web/src/lib/privacy/consent-events.ts`. These records are **never updated or deleted** in normal app flows. Service functions: `appendConsentEvent`, `appendConsentEventBestEffort`, `listConsentEvents`. Constants for event/document types: `CONSENT_EVENT_TYPES`, `CONSENT_DOCUMENT_TYPES` in `apps/web/src/lib/privacy/types.ts`.
- **Consent authorization.** Only family `admin` users may record consent, re-accept terms/privacy, or view the consent history. Child `player` accounts receive `403` on all `/api/family/privacy/*` routes. Firestore rules enforce `isFamilyAdmin` for both read and create on `consentEvents`; update/delete are denied at the rules level.
- **Version bump triggers re-acceptance.** When `CURRENT_TERMS_VERSION` or `CURRENT_PRIVACY_VERSION` changes, any family whose stored versions differ will show `consentUpToDate: false`. The Privacy tab surfaces a prominent warning callout and the "Record Consent" action re-accepts the current versions and appends new consent events.
- **Support access must stay scoped.** Apply `Support Access Rules` to `/support`, support APIs, and manual operator workflows. `ADMIN_ONLY` data stays limited to the active support workflow.
- **Support visibility.** `GET /api/support/privacy` surfaces families with missing or outdated consent in `consentHealthFamilies`, plus recent consent events via a collection-group query on `consentEvents`. The Privacy & Compliance panel on `/support` shows consent health stats and event history without exposing unnecessary private family data.
- **No new top-level Firestore collections required.** `consentEvents` is a subcollection under `families/{familyId}`, consistent with `auditLogs`, `notifications`, and other family-scoped subcollections.
- **Support visibility (web-only):** operators see deletion-requested families and recent privacy audit activity via `/api/support/privacy` + the Privacy & Compliance panel on `/support` (Families module). Never expose unnecessary child detail there.
- Family data export and deletion workflows must remain supported as the schema evolves.
- Onboarding routing + duplicate-child prevention (2026-06-08):
  - **Terms/consent acceptance only records consent — it must never reset onboarding, family, or children state.** `POST /api/family/privacy/consent` writes consent fields exclusively and does not touch `onboardingCompletedAt`. Do not add onboarding/family-state writes to consent routes.
  - **A family that already has children must never be routed back into the new-family onboarding wizard.** The onboarding routing decision lives in one pure function, `computeOnboardingDecision` in `apps/web/src/lib/family/onboarding.ts`, used by `GET /api/family/onboarding-status`. Do not recompute `needsOnboarding` inline from consent/onboarding timestamps alone (the old `!(onboardingCompletedAt || parentalConsentAt)` rule caused the P0 duplicate-child bug for pre-version-tracking families). The decision counts active `player` members; structural redirect target is: no family → `family_setup`, family with 0 children → `child_setup`, family with children → `dashboard`.

Regular family-management adds are never blocked — keep that distinction when touching this route. The onboarding wizard's AddChild step sends `source: "onboarding"` and `onboardingFirstChild` only for the first add in the session.
  - **Duplicate-child cleanup is support-only, soft-delete, and activity-guarded.** `GET/POST /api/support/duplicate-children` (Families module panel) detects same-family/same-name duplicate children and soft-deletes only empty, non-original duplicates. Detection/safety logic is the pure `findDuplicateChildGroups` / `hasMeaningfulActivity` in `apps/web/src/lib/support/duplicate-children.ts`. Never hard-delete a child, and never delete one with chores, completions, coins, wallet ledger, inventory, or achievements — the POST handler re-verifies activity server-side before deleting.
  - **Structured logs:** `[ONBOARDING_REDIRECT_DECISION]`, `[FAMILY_MEMBER_CREATE]`, `[ONBOARDING_DUPLICATE_CHILD_PREVENTED]`, and `[SUPPORT_DUPLICATE_CHILD_SOFT_DELETED]` carry `user_id`/`family_id`/`child_count`/`child_creation_source`/`redirect_target` for tracing. Preserve these when refactoring.

## New Skill Bonus (2026-06-11)
- **What it is.** A child earns a one-time **+5 coin** "New Skill Bonus" the first time they ever complete a given chore. User-facing copy is always "New Skill Bonus" (never "New Chore Bonus"). Amount: `NEW_SKILL_BONUS_AMOUNT` in `apps/web/src/lib/chores/skill-bonus.ts`.
- **Once per child per chore/root recurring chore.** The bonus is granted per *child*, not per family, and only on the first completion of a chore *identity*. Recurring completions spawn a fresh chore doc; the canonical identity is the **root** chore of the series (`recurrenceRootChoreId`, propagated on spawn, with `recurrenceParentChoreId` as a one-level fallback for legacy docs). `canonicalRecurringChoreId(fields, choreId)` resolves it. For MVP, copied/recreated chores count as a new skill (new `chore_id`/root).
- **Idempotent, awarded at the normal coin lifecycle point.** Award happens at the *same* moment as normal chore coins: immediately on completion when no approval is needed, or at approval time when approval is required (`action: "complete"` reaching `Approved`, and `action: "approve"`). A durable claim record at `families/{familyId}/skillBonuses/{playerUid__rootChoreId}` is created with an `exists:false` precondition (`commitWrites`), so retries, websocket replays, and double-approvals cannot double-award. Wallet credit uses reason `new_skill_bonus` with a deterministic ledger id. Claim-then-pay ordering means a rare wallet failure skips the bonus rather than double-paying.
- **Kiosk Mode awards the active kiosk player.** In Kiosk Mode the session identity is the selected player, so the bonus (like the normal payout) is paid to the resolved assignee/kiosk player, never the authenticated parent account.
- **Events expose bonus metadata.** Completion/approval notification + realtime + response payloads carry `newSkillBonusAwarded` / `newSkillBonusAmount` (and the API response includes `newSkillBonus` only when awarded). Existing websocket refresh behavior is unchanged.
- **Dashboard chore rows expose compact metadata.** `GET /api/family/summary` returns `newSkillBonusEligible` + `newSkillBonusAmount` per chore (computed only for clearly single-assignee chores against the family's claimed-bonus key set; omitted for multi/family chores to avoid over-promising). The dashboard card shows a compact "New Skill +5" badge when eligible, and a recurring chore shows a calendar icon that toggles to a short frequency label on click (local state, resets to the icon on reload). Icon/label use button semantics with accessible labels and never rely on color alone.
- **Classification.** `skillBonuses` is a `families/{familyId}` subcollection (`FAMILY_PRIVATE` / `CHILD_SENSITIVE` — per-child completion history); no new top-level collection.
- **Do not repurpose chore categories as Responsibility Pillars / skill concepts.** Existing chore categories stay categories; skill/pillar concepts are not built on them yet.

## Responsibility Pillars (2026-06-11)
- **Product vision.** Family Chores is positioned as a platform that helps parents intentionally develop capable, independent, responsible young adults — not just a gamified chore chart. Large responsibilities are learned through small, repeatable tasks. Responsibility Pillars are a **core architectural concept**: preserve and extend them rather than working around them. Homepage messaging is growth-centered ("Help your children grow into capable, confident, and responsible adults"), and future SEO content (age-appropriate chores, printable routines, life-skill guides) is built around pillars.
- **The five pillars.** `home_care` 🏠, `self_care` 🌱, `organization` 📋, `family_contribution` 🤝, `life_skills` 🛠 — canonical ids in `RESPONSIBILITY_PILLARS` (`apps/web/src/lib/responsibility/types.ts`). Display names are localized under `responsibility.pillars.*`; never hardcode pillar display names in family-facing UI.
- **Pillars are NOT Categories.** Existing chore Categories are user-defined organizational labels ("where does this chore belong?"). Pillars answer "what life skill does this chore develop?". Do not repurpose, merge, or derive one from the other. `responsibilityPillar` is a separate optional field on chore docs.
- **Pillar assignment is always optional and must never break existing flows.** `normalizeResponsibilityPillar` maps unknown/missing values to `""`; chores/routines without a pillar simply award no XP, silently. Recurring chore spawns propagate `responsibilityPillar` to the next occurrence.
- **XP architecture: additive and event-driven.**
  - Events: `families/{familyId}/responsibilityXpEvents/{id}` — append-only awards (`playerId`, `pillar`, `xpAwarded`, `eventType`, `choreId`/`routineId`, `createdAt`). Event types: `chore_completed`, `routine_step_completed`, `routine_completed`, `new_skill_bonus`.
  - Aggregate: `families/{familyId}/responsibilityProgress/{playerUid}` — per-pillar XP (`xp_<pillar>`), `totalXp`, `skillsLearned`, `routinesCompleted`. Maintained alongside each event write (`recordResponsibilityXpAward` in `apps/web/src/lib/responsibility/service.ts`); never recalculated from scratch on read.
  - Levels are **derived** from XP against configurable thresholds (`apps/web/src/lib/responsibility/levels.ts`; defaults 0/100/250/500/900, extrapolating past the list by the last gap).
  - Configuration: XP values + thresholds are tunable via the support console, stored at `appConfig/responsibility`, loaded with admin credentials + 60s in-memory cache, falling back to code defaults (`apps/web/src/lib/responsibility/config.ts`). Defaults: chore +5, routine step +5, routine completion bonus +15, New Skill Bonus +10.
  - XP awards are **best-effort**: failures log and are swallowed; they must never break chore completion/approval or routine flows.
- **Award lifecycle matches coins.** Chore XP is awarded at the payout lifecycle point (immediate completion or approval) in `apps/web/src/app/api/chores/[choreId]/route.ts` via `awardChoreResponsibilityXpBestEffort` — chore XP per paid player, plus New Skill XP for players who earned the New Skill Bonus, all under the chore's pillar. Kiosk Mode attributes XP to the active kiosk player (session identity), never the authenticated parent.
- **Routines are the canonical mechanism for teaching larger life skills** through repeated, structured experiences. Treat them as first-class objects, split into two layers that must never be conflated:
  - **Routine (template)** — `families/{familyId}/routines/{id}`: reusable parent-defined definition (name, `description`, pillar, `stepsJson`, completion bonus XP/coins, `timesUsed`, `timesCompleted`, `active`). CRUD is admin-only via `/api/routines` + `/api/routines/[routineId]`; managed on the `/routines` page (`RoutinesPageClient`: table with name/pillar/steps/times-used/last-updated and Create/Edit/Duplicate/Delete/Assign actions). Max 50 routines per family, 20 steps per routine.
  - **RoutineAssignment (instance)** — `families/{familyId}/routineAssignments/{id}`: one occurrence assigned to one player (`POST /api/routines/[routineId]/assign`, admin only). Assignment **snapshots the steps** (`stepsJson` incl. per-step `choreId` + `coinValue`), so editing or deleting a template never rewrites in-flight or historical assignments. Model/helpers in `apps/web/src/lib/responsibility/assignments.ts`; lifecycle in `assignment-service.ts`.
  - **Steps are materialized as ordinary chore documents** (fields `routineAssignmentId`, `routineId`, `routineName`, `routineStepId`, `routineStepOrder`, `routineStepCount`, plus `responsibilityPillar` and a `responsibilityXpReward` override set to the configured routine-step XP). This is the load-bearing design decision: completion, parent approval, the New Skill Bonus, Kiosk Mode, and the activity feed all work on routine steps with zero special-casing. Step chores never recur individually — recurrence lives on the assignment, which respawns a fresh assignment + chores when it completes (mirroring how recurring chores clone on completion).
  - **Progress + rewards.** The chore PATCH route calls `recordRoutineStepCompletionBestEffort` at the payout lifecycle point (immediate complete or approval). It marks the step done on the assignment; on the final step it pays the completion bonus coins (wallet reason `routine_completion_bonus`, ledger id keyed by assignment id → idempotent), awards routine-completion pillar XP, bumps `routinesCompleted` + the per-routine `routineCompletionsJson` stats on the player's progress doc (`recordRoutineCompletionStatsBestEffort` — counted even for pillar-less routines), bumps the template's `timesCompleted`, and emits a `routine_completed` activity. Undoing a paid step re-opens it in the assignment but never claws back an already-paid routine bonus.
  - **Dashboard rendering.** Chore lists collapse routine siblings so only the **next incomplete step** per assignment shows (`collapseRoutineChores` in `apps/web/src/lib/responsibility/routine-chores.ts`; used by the today panel and kiosk). Routine-linked rows show a routine badge ("name + step N/M"); clicking opens the read-only **routine progress dialog** (`RoutineProgressDialog`, fed by `GET /api/routines/assignments/[assignmentId]`) showing steps done/remaining, pillar, and routine-level rewards.
  - **Assignment workflow.** The dashboard "+ Add ▼" menu offers Chore (existing flow, unchanged) or Routine (`AssignRoutineDialog`): autocomplete over family routines (with inline "create new" if no match), step preview + customize (add/remove/reorder — affects only this assignment), an explicit unchecked-by-default "Update the saved Routine with these changes" checkbox, then player/due date/recurrence/coins-per-step/approval.
  - Family activity kinds: `routine_created`/`routine_updated`/`routine_assigned`/`routine_completed` (mirrored in the ws server's `FAMILY_ACTIVITY_TYPES` — both copies must stay in sync). The family feed surfaces only `routine_assigned` and `routine_completed`; per-step progress is covered by the normal `chore_completed` events (whose messages carry "step N of M in the X routine" context) to avoid feed spam.
- **Child profile.** The "Responsibility Progress" card (`ResponsibilityProgressCard`) renders per-pillar bars/levels + totals from `GET /api/responsibility/progress` (self; admins may pass `?memberId=`).
- **Chore Suggestions + Community Routine Library (foundation, no AI, no public publishing yet).** Top-level support-curated collections: `responsibilityChoreSuggestions` (title, pillar, min/max age, difficulty, estimated minutes, popularity, active) and `communityRoutines` (steps, pillar, age range, `status` pending/approved/rejected, `featured`). Family-facing reads are session-gated and served with admin credentials: `GET /api/responsibility/suggestions` (filters: pillar/age/difficulty/maxMinutes) and `GET /api/responsibility/community-routines` (approved only, `?featured=1`). Parent publishing into the community library is intentionally not exposed yet.
- **Support console.** `/support/responsibility` (module id `responsibility`): pillar reference, XP/threshold configuration, suggested-chore CRUD, community-routine moderation (approve/feature/reject), and analytics (capped collection-group scan of `responsibilityXpEvents`; per-age distribution is future work pending player age data). APIs under `apps/web/src/app/api/support/responsibility/`.
- **Future integration points.** Chore Suggestions recommendations ("my child is behind in Home Care"), parent-published community routines, achievements granting pillar XP (event model is extensible via new `eventType`s), per-age analytics, and pillar-driven SEO pages.
